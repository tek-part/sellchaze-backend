Observed EasyOrders2.4.25: an active WhatsApp OTP plugin describes one-time codes
for identity/false-order reduction. Separate blocked-phones list/create requires
phone_number. The phone-verification settings tab binds the merchant account,

The public product banner link did not expose a usable OTP checkout for inspection.

Owner/store.settings.manage configures encrypted per-store Wawp credentials and
required OTP. New credentials must pass the fixed-origin session/info check before
enablement. Replacement/clearing is explicit, saved credentials never returned,
optimistic settings versions reject stale writes. Each settings update rotates
a generation, invalidating previous challenges/proofs. Existing digital WhatsApp
credentials remain separate. No live Wawp acceptance was performed in this pass.

Both ordinary and direct/funnel checkout force a valid phone when enabled, even
email-only digital baskets. The same CheckoutService consumes a verified proof
under the existing Store lock for guest/direct/signed-in flows. Proof is bound to
store, canonical E.164 phone, current generation and a256-bit browser secret.
Consumption and order/cart/stock/coupon/digital-code allocation share a transaction;
failure restores proof availability. Used proof records link to the resulting
order. A second new order cannot reuse it. Idempotent replay, receipts and payment
retry for existing orders remain available after expiry/block/settings changes.

Random six-digit codes expire after300 seconds, allow5 failed/correct verification
attempts, and are replaced rather than refreshed on resend. Correct verification
deletes the code digest and grants a proof lasting300 seconds. Code and bearer
digests use HMAC-SHA256 with the application key; neither cleartext codes nor bearer
tokens are stored in the database/model JSON/log messages. A256-bit client nonce
gives retry-safe sends without returning any code. Lost send responses retry the
same nonce. A durable dispatch claim precedes provider I/O, so crashes/ambiguous
transport outcomes never cause automatic resend. Failed/uncertain outcomes cannot
verify. Provider acceptance/queue admission is not a delivery acknowledgement.
Expired/superseded/used/config-stale proofs fail closed. Repeated successful verify
is idempotent until proof expiry and does not extend its deadline.

Limits count all dispatch attempts:60-second cooldown per canonical number,
3/hour and10/24h per number,10/hour per hashed IP per store,300/hour per store.
DB checks/claims serialize with Store locks, independent of numeric route throttle
10 sends/min and30 verify requests/min. MySQL concurrency/throughput remain pending;
SQLite tests cannot prove row-lock behavior. Phone blocks stop new sends and any
later verify/consume; an external send already underway cannot be recalled.

OTP blocks use scope=otp and checkout blocks scope=checkout in the shared canonical
block table; uniqueness is(store,scope,canonical phone). Lists, mutations/history
validate their scope, preserving existing checkout records. OTP list does not ban
purchase when OTP is disabled. Both lists support notes, versions, reversible
unblock, canonical search and private actor history. Order-only employees can
manage blocks but cannot read/change provider settings.

Migration180000 adds Store OTP columns, scope and challenges. Default disabled
preserves old flows. Rollback deletes OTP-only block/events to avoid converting
them into checkout bans, retains checkout blocks, and removes OTP challenge data.
Install both repository versions and migrate before enabling. Daily scheduled
checkout-otp:prune clears expired code digests and removes unused records older
than30 days; consumed order-linked proof records remain for audit.
