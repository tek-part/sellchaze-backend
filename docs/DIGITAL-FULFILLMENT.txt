Private guest receipt:
Checkout success, payment-start failure/retry and idempotent replay expose a
purpose-specific HMAC receipt capability lasting30days. POST checkout/receipt
accepts the token in its JSON body and checks tenant, signature and expiry before
returning the customer order resource. Order numbers and payment-retry tokens
grant no receipt access. Responses are private/no-store; merchant notes and
timeline are excluded. Delivery still requires a paid, noncancelled order.
The browser saves the capability per origin/order in session storage (memory
fallback), preserves it across provider redirects and puts it in the fragment
of the private share link. The receipt panel saves/removes an incoming fragment
from the current URL. Normal page requests and referrers omit fragments.
Receipt UI also renders below merchant-configured success templates.

Bank transfer:
At transaction creation, whitelist account_name/bank_name/iban/swift_code and the
public checkout note into its metadata. Existing orders retain those instructions
after settings change. Legacy transactions without the snapshot show no banking
details; the buyer contacts the store. Unrelated credentials never reach buyers.
Instructions are only returned through the private receipt while awaiting payment.

POST my-store/orders/{id}/payment/confirm-bank (also stores/{store}/orders/...)
requires store.orders.manage and the normal owner/admin tenant scope. A required
reference and optional internal note are validated. The service locks transaction
and order, checks bank method, pending transaction, noncancelled order and exact
amount/currency. It marks both paid, records actor/reference/note on the merchant
timeline and records one durable paid-digital event in the same transaction.
Same-reference repeat is idempotent; different reference or mismatched state fails.
It does not independently advance the physical shipping lifecycle. Merchant UI
requires a concrete review of amount/reference before confirmation.

Paid delivery:
Verified provider webhooks also record the digital event only on the order's first
unpaid-to-paid transition. The outbox payload contains only tenant/order IDs,
never links/codes/tokens. Existing scheduled outbox:publish delivers a localized
HTML mail with escaped codes/link snapshots and a private canonical-store receipt.
The listener explicitly scopes order/items without requiring CurrentStore; it
rechecks paid/noncancelled state and skips cancelled orders. Catalog deletion
does not remove immutable fulfillment. SMTP failures get a sanitized error and
existing exponential retries (max5; exhausted messages remain failed_at).
One stable Message-ID is used per event. Duplicate confirmations, provider events
and successful publisher re-runs do not produce new mail events.
SMTP is an external side effect: a crash after server acceptance but before DB
acknowledgement can produce a duplicate retry. Exactly-once SMTP is not claimed.

Replays now refresh the live order/payment state, receipt and private attachment
links instead of showing ready delivery beside stale pending order/payment data.

Prepayment and merchant email follow-up (2026-10-10):
Checkout now records a separate StorefrontDigitalReceipt event for immutable
digital/mixed order snapshots. A private receipt mail contains order/total,
the saved bank-instruction whitelist and a purpose-separated private link. It
never contains digital codes or URLs. If bank payment transaction creation is
still in progress, publication retries rather than sending empty instructions.
Paid-before-publication or cancelled orders skip the prepayment message; paid
digital delivery still uses its separate durable event.

GET/POST orders/{id}/digital-email requires tenant scope and store.orders.manage.
GET returns only two latest email states: not_scheduled/queued/retrying/failed/
sent/skipped/processed, attempt count and sanitized timing/error information.
"Sent" means handed to the configured mail transport, not inbox confirmation.
Historical paid events lacking mail_outcome metadata are labelled processed.
POST accepts kind, expected message_id and a UUID request_key. It rechecks live
order eligibility under a lock, rejects a stale message, queued email or send
within 60 seconds of publication, and records a new audited ID-only event.
An exhausted event remains failed for history; retry does not erase attempts.
Same-key replay returns the existing result; using the key for another kind
fails. No recipient override is accepted: the saved order email is used.
The publisher and merchant service use event-before-order locking. Simultaneous
MySQL acceptance is still pending; SQLite integration proves serial replay.

Merchant UI shows saved recipient and localized status, requires review before
queueing, and retains the request key after an uncertain HTTP result. Refreshing
status does not create an email. Delivery resend requires paid/noncancelled state;
receipt resend requires unpaid/noncancelled state. Recipient edits are not exposed.
