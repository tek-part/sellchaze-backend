Owner/store.settings.manage configures a separate encrypted site/secret key pair
per store. Saved secrets are hidden from model/API JSON. Public checkout fields
expose only enabled, public site key, action and revision. Settings use an optimistic
version and every change rotates generation. Saving keys never claims a working
provider connection: acceptance requires an actual widget challenge/siteverify.

Initial/default disabled preserves unconfigured stores; configured production
activation and automatic platform-wide protection remain rollout/parity work.

The official explicit widget is loaded only when required. Arabic/English shared
cart/funnel form uses a compact widget, pending/error/expiry/retry states and gates
new-order CTA until the server accepts proof. Widget callbacks alone do not unlock
checkout. Locale/configuration/retry replace the256-bit client nonce. Stale async
responses cannot restore invalidated proof. Widget errors/expiry clear readiness.
Existing private receipt and payment-retry flows remain independent of new checks.

Fixed-origin HTTPS siteverify has bounded connection/request timeouts and no
redirects. Validation requires strict boolean success, exact checkout action and
nonce cdata, an ISO timestamp with at most5 seconds future skew, and an allowlisted
hostname. Hostnames derive from verified domains and the platform slug; localhost
and127.0.0.1 are allowed only local/testing. Unverified custom domains never count.
Expiry uses original provider challenge time plus300 seconds, not validation time.
No failure/malformed/unknown provider response grants proof. No raw provider token,
secret, client nonce or IP is persisted in the challenge model/database/log text.

Nonce/token/IP digests use HMAC with the application key. A durable checking claim
commits before provider I/O; exact retries return existing state without spending
the token again or extending its deadline. Global token uniqueness rejects reuse
by another nonce/store, including a database uniqueness race. Crash/lost-provider
responses fail closed: obtain a fresh widget token. IP40/10minutes and store1000/hour
budgets include failed/pending attempts and serialize under the Store lock; route
throttle is10/minute. These controls are not a claim that all bots are eliminated.
The app's trusted-proxy configuration determines the IP used for binding/budgets.

CheckoutService rechecks enabled/generation/store/nonce/IP/state/strict expiry under
the existing Store lock. Consumption and order/cart/stock/coupon/code allocation
share one transaction, so later checkout failure restores availability. Consumed
checks link to their order; a second new order cannot reuse proof. Durable checkout
idempotency replay/recovery continues after check expiry or configuration change.
Checking claims that lose their process remain unusable, not automatically retried.
Daily checkout-bot:prune removes unused checks older than30 days, retaining consumed
order audit. Migration190000 is default-disabled and reverses by dropping bot data.
