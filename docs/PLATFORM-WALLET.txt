Platform wallet and account referrals

User-approved policy, 2026-10-12: $0.04 per NEW storefront order; hide NEW
merchant order details at five fees of debt; 20% cash commission from new
confirmed wallet funding by referred accounts. Historical orders are exempt.

The platform USD ledger uses signed integer thousandths, independent of store
checkout currencies, customer payments, legacy B2B balances and cash commission.
Every confirmed receipt has one globally unique event key. Exact retries return
the original event; conflicting receipt reuse fails with 409. Refunds cannot
exceed the original funding; cumulative commission reversal preserves rounding.
Funding/payout/refund reconciliation requires an authenticated Admin, USD,
confirmed=true and the actual operator ID. This records independently confirmed
settlement; it does not itself collect, transfer or refund external money.

Referral codes are random UUIDs, explicitly generated by account owners. GET
does not mint profiles. Only first valid signup binds the referrer, including
pending Google merchant registration. Existing sign-ins cannot change referral.
The cash commission stays outside the spendable wallet. A confirmed payout needs
sufficient commission and ten distinct invited accounts with created stores.
Replaying a funding event cannot accrue retroactive commission after enablement.

Migrations 090000, 100000 and 110000 add seven tables without rewriting orders.
Their empty reversals/reapplications are verified; financial/profile rows or an
active cutover refuse destructive reversal. Keep their history on rollback.

Order charging remains OFF until the merchant funding flow is operational.
To activate after that prerequisite: enable PLATFORM_WALLET_FEES_ENABLED and run
php artisan platform-wallet:activate-order-fees. The command saves max existing
store_order ID once. Repeating it retains the same boundary. CheckoutService
charges inside the order transaction, so checkout recovery and payment retry
cannot charge twice. Legacy orders and uncharged orders remain visible.
At debt >= $0.20, merchant lists omit charged orders, report a locked count, and
details/notes/payment confirmation/digital operations/shipment routes return402.
The B2B API also filters the owner's charged bridges and guards private details.
The customer API remains operational, including receiving another order at debt.
Disabling fees is reversible; never delete ledger entries or reset the cutover.

GET /api/v1/me/platform-wallet: actual balance, due, fee activation/lock state.
GET /api/v1/me/platform-wallet/entries: owner-only paginated/sortable statement;
each real entry projects an informational balance row, without another debit.
GET/POST /api/v1/me/platform-referral: actual cash/referrals and explicit minting.
POST /api/v1/admin/platform-wallet/reconcile: funding/refund/payout settlement.
Public receipt payloads never include platform commission or ledger references.

Frontend /top-up, /transactions and /referral are owner routes. The signup
capture uses only its own session-storage key, expires after30 days, honors
DNT/GPC/preview, and never clears unrelated auth/cart/session data.

Fawaterak API v2 implements hosted wallet funding for the seven USD presets:
5,10,20,50,100,200,600. Configure PLATFORM_WALLET_FAWATERAK_ENABLED, TEST_MODE,
API_KEY, VENDOR_KEY and the public HTTPS webhook base in private server settings.
The platform account is separate from every tenant's customer payment gateway.
Each payment keeps encrypted credential/mode snapshots, one durable request UUID,
and server-side USD amount. No API credential reaches the client. A pending or
uncertain attempt prevents a second attempt until reconciliation/expiry. A lost
creation response is never submitted twice. Signed callback plus authenticated
getInvoiceData must match invoice ID/key, original UUID, currency, amount and
paid state. The browser return URL cannot credit money. Exact duplicate callbacks
return success without another ledger entry. Test invoices do not add spendable
credit or referral commission. A signed paid callback can recover a lost creation
response by UUID after the same server-side checks. GET pages only read data.
POST owner refresh verifies payment, and preserves another account's privacy.
